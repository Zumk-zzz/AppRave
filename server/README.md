# AppRave — бэкенд

API и база для мобильного приложения ночного клуба.

## Стек

Node 20+ · TypeScript · Fastify · Prisma · PostgreSQL 17 · Docker Compose

Redis не используется: атомарность продаж держит сама база через условный
`UPDATE`, а сессии — на JWT. Отдельное хранилище для блокировок не нужно.

## Запуск

```bash
docker compose up -d
```

```bash
npm install && npx prisma migrate deploy && npm run dev
```

База поднимается на **порту 5433**, а не 5432: на машине разработчика
5432 занят нативной службой PostgreSQL, и трогать её незачем.

Подключиться к базе руками:

```bash
docker exec -it apprave-db psql -U apprave -d apprave
```

## Как устроена защита от «покупок просто так»

Три механизма, и все три живут в базе, а не в коде приложения.

**1. Резерв с таймером.** Заказ создаётся в статусе `pending`, товар сразу
списывается, но у заказа стоит `expires_at` (15 минут). Оплатили — `paid`.
Не успели — фоновая задача переводит в `expired` и возвращает товар в продажу.

Без резерва пришлось бы выбирать между двумя плохими вариантами: держать
товар с момента добавления в корзину (брошенные корзины заблокируют весь
зал) или списывать только после оплаты (двое дойдут до платёжной формы за
один последний билет).

**2. Атомарная продажа билета.** Никаких «прочитать, проверить, записать» —
между этими шагами и возникает гонка. Всё одним запросом:

```sql
UPDATE ticket_types
   SET sold = sold + $qty
 WHERE id = $id AND sold + $qty <= quantity
RETURNING id;
```

Вернулась строка — билет ваш, вернулось пусто — разобрали. Одиночный
`UPDATE` сам берёт замок на строку, ручные блокировки не нужны.

Поля `quantity` и `sold` разделены намеренно: первое правит администратор,
второе пишет только система. Доступное считается как разница и нигде не
хранится, поэтому редактирование события во время продаж ничего не затирает.

**3. Бронь стола — частичный уникальный индекс.**

```sql
CREATE UNIQUE INDEX one_live_booking_per_table
    ON table_bookings (event_id, table_id)
 WHERE status IN ('pending', 'paid');
```

Живыми считаются только `pending` и `paid`, поэтому отменённая бронь
освобождает стол. Обычный уникальный индекс запретил бы и повторную бронь
после отмены — а это ровно то, что должно работать.

Проверить, что всё это действительно работает:

```bash
docker exec -i apprave-db psql -U apprave -d apprave -q -f - < scripts/integrity-check.sql
```

Скрипт имитирует гонку двух покупателей за последний билет и двойную бронь
стола, затем откатывает всё за собой.

## Статусы

Заказ:

```
draft → pending → paid → used
           ↓        ↓
        expired  refunded
           ↓
       cancelled
```

Событие: `draft` → `published` → `cancelled`. Черновик не виден гостям,
чтобы полупустая карточка не попадала в афишу.

## Оплата

Сейчас заглушка: провайдер `stub`, платёж подтверждается вручную через
служебный эндпоинт. Настоящий шлюз подключается заменой одной реализации.

Два правила, которые не должны нарушаться при подключении реального шлюза:

- заказ становится `paid` **только** по вебхуку от шлюза, никогда по слову
  клиента;
- и создание заказа, и обработка вебхука идемпотентны — двойной тап по
  кнопке и повторная доставка вебхука не должны создавать второй заказ
  или списывать деньги дважды.

## Деньги

Везде целые числа в копейках (`price_kopecks`, `total_kopecks`).
`float` не используется нигде: на нём 1500.00 однажды станет 1499.9999999.
